# ⚙️ Проект «Автозапчасти» — Лабораторные работы по ADO.NET (PostgreSQL)

Реализация **10 практических задач** по работе с базами данных в связке **C# + ADO.NET + PostgreSQL (Npgsql)**. Проект разработан в среде **Visual Studio** как единое консольное веб-приложение на базе ASP.NET Core Web SDK без использования сторонних ORM (Entity Framework и др.). Вся логика реализована на «чистом» ADO.NET для демонстрации глубокого понимания работы с СУБД.

## 🚀 Как запустить проект локально

Проект настроен на работу с локальным сервером PostgreSQL (например, запущенным через Docker).

1. **Запустите PostgreSQL**: Убедитесь, что ваша база данных запущена. По умолчанию проект использует следующие параметры подключения:
   * **Хост**: `localhost`
   * **База данных**: `parts_db`
   * **Логин**: `postgres`
   * **Пароль**: `1234`
2. **Скомпилируйте проект**: Откройте проект в Visual Studio и соберите его (**Ctrl + Shift + B**).
3. **Запустите приложение**: Нажмите **F5** (или кнопку Start). Откроется консольное окно веб-сервера.
4. **Перейдите в браузер**: Веб-интерфейс доступен по локальному хосту. Откройте браузер и перейдите по адресу:
   ```http
   http://localhost:5000/Parts/Search
   ```

*Примечание: Если интерфейс выглядит как неразмеченный текст, убедитесь, что в профиле запуска Visual Studio установлен режим `ASPNETCORE_ENVIRONMENT=Development` для успешной загрузки стилей Bootstrap через CDN.*

## 📝 Что было сделано (10 выполненных задач)

В рамках проекта в едином файле были успешно реализованы следующие задания:

### 1. Поиск запчастей по названию и артикулу
Добавлен метод `SearchParts(string query)` с использованием параметризованного запроса и оператора `ILIKE` (`@q`, значение `"%{query}%"`). Обеспечена регистронезависимость и полная защита от SQL-инъекций (`AddWithValue`).

### 2. Удаление запчасти с проверкой результата
Реализован метод `DeletePart(int id)`. Логика завязана на анализ возвращаемого значения метода `ExecuteNonQuery()`. Если количество затронутых строк равно нулю, пользователю выводится понятная ошибка.

### 3. Статистика по складу одним запросом
Реализован метод `GetStats()`, возвращающий кортеж `(int, decimal, decimal)`. Используются SQL-агрегаты `COUNT(*)`, `SUM` и `AVG`, а также функция обработки `NULL` значений — `COALESCE`. Данные вычитываются за один проход через `NpgsqlDataReader`.

### 4. Оформление заказа в транзакции
Разработан метод `PlaceOrder(...)`. В рамках одной транзакции (`BeginTransaction`, `Commit`/`Rollback`) происходит проверка остатка товара на складе (`FOR UPDATE` блокировка от race condition), списание количества и вставка записи в таблицу `orders`.

### 5. Массовое поступление товара с откатом при ошибке
Метод `Restock(...)` принимает список позиций для обновления склада. Изменения выполняются циклом внутри одной транзакции. Если хотя бы один ID детали не найден в базе (`ExecuteNonQuery() == 0`), вся транзакция полностью откатывается (`Rollback`).

### 6. «Сырое» чтение через NpgsqlDataReader
Реализован метод `GetRawParts()`, который делает выборку без использования готовых C# моделей (класса `Part`). Строки динамически раскладываются в коллекцию `List<Dictionary<string, object?>>` с использованием низкоуровневых свойств ридера: `FieldCount`, `GetName`, `GetValue` и `IsDBNull`.

### 7. DataTable через NpgsqlDataAdapter
Продемонстрирован отсоединённый режим работы с данными. Метод `GetPartsDataTable()` заполняет структуру `DataTable` с помощью `NpgsqlDataAdapter.Fill()`, после чего строки и колонки динамически рендерятся на веб-странице.

### 8. Асинхронная версия GetAllParts
Написан метод `GetAllPartsAsync()`. Всё взаимодействие с базой переведено на неблокирующие асинхронные потоки с использованием ключевых слов `await using`, `OpenAsync()`, `ExecuteReaderAsync()` и `ReadAsync()`.

### 9. Обработка уникального ограничения (SqlState)
На таблицу `parts` наложено ограничение `UNIQUE(article)`. Метод добавления `TryAddPart(...)` перехватывает специфичное исключение базы данных `PostgresException` и по коду ошибки `SqlState == "23505"` возвращает пользователю бизнес-предупреждение вместо падения сервера с ошибкой 500.

### 10. Пул соединений и Maximum Pool Size
Создан стресс-тест эндпоинт `/Parts/PoolTest`, который одновременно запускает 20 асинхронных задач к базе данных. В строке подключения жестко ограничен пул соединений (`Maximum Pool Size=5`). В коде подробно задокументировано, почему конструкция `using / Dispose` не закрывает физическое TCP-соединение с PostgreSQL, а возвращает его в пул для повторного использования.
