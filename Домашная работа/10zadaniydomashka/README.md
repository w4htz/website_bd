# Лабораторная работа: Продвинутая асинхронная работа с PostgreSQL в ADO.NET (Npgsql)

Репозиторий содержит готовые, высокопроизводительные решения ключевых задач по работе с СУБД **PostgreSQL** из среды **.NET 10** с использованием официального асинхронного драйвера **Npgsql**. 

Проект реализован в виде консольного приложения C# (Top-Level Statements) без использования тяжелых ORM и Docker-контейнеров, демонстрируя чистую работу с уровнем доступа к данным (DAL) и особенности протокола PostgreSQL.

## 📌 Ключевые особенности реализации
* **Полная асинхронность:** Применение `await using` для `NpgsqlConnection`, `NpgsqlCommand` и `NpgsqlDataReader` для предотвращения блокировок потоков (Thread Pool Starvation).
* **Контроль контекста:** Использование `.ConfigureAwait(false)` во всех библиотечных методах для оптимизации работы с пулом потоков и исключения дедлоков.
* **Таймауты и отмена:** Связывание токенов пользователя (`CancellationToken`) с жесткими клиентскими и серверными лимитами времени (`statement_timeout`).
* **Безопасность:** Исключительно параметризованные SQL-запросы для защиты от SQL-инъекций.

## 🛠 Выполненные задачи и архитектурные решения

### Задача 1. Базовый асинхронный репозиторий с пагинацией и отменой
Реализован метод `GetEmployeesAsync` для постраничной выборки сотрудников. В коде связано два уровня таймаута: жесткий лимит сокета на клиенте (`CommandTimeout = 10`) и общий лимит операции (`CancelAfter(15)`).

* **Особенности работы таймаутов:** При срабатывании клиентского `CommandTimeout` (socket timeout) драйвер Npgsql принудительно разрывает текущее физическое TCP-соединение с сервером СУБД из соображений безопасности. Серверный `statement_timeout` действует иначе: сам сервер PostgreSQL прерывает выполнение конкретной тяжелой команды и возвращает ошибку с кодом `57014`, при этом сетевое сокет-соединение остается живым в пуле и готово выполнять следующие команды.

### Задача 2. Массовая вставка данных через бинарный протокол COPY
Реализован импорт тысяч записей в таблицу заказов через `BeginBinaryImportAsync`. Настроен вызов асинхронного прогресс-индикатора `IProgress<int>` каждые 10 000 строк.

* **Производительность механизма COPY:** Метод `COPY` минует стадии парсинга единичных SQL-строк, построения планов выполнения для каждой записи, а также нивелирует накладные расходы на сетевые round-trip'ы (запросы туда-обратно), передавая данные сплошным бинарным потоком напрямую в подсистему хранения. Вызывать `CompleteAsync()` после исключения категорически запрещено, иначе частично поврежденные или незавершенные данные зафиксируются в БД. Благодаря `await using` при возникновении ошибки `importer` уничтожится, автоматически выполнив `ROLLBACK`.

### Задача 3. Асинхронные транзакции с гарантированным откатом
Реализован безопасный перевод денежных средств между счетами на максимальном уровне изоляции `IsolationLevel.Serializable`. Блокировка строк от параллельного изменения реализована через SQL-конструкцию `FOR UPDATE`.

* **Откат транзакций в PostgreSQL:** В PostgreSQL любая ошибка внутри транзакции безвозвратно переводит текущую сессию в состояние `aborted` — ядро СУБД блокирует любые последующие команды, выдавая ошибку *«current transaction is aborted, commands ignored»*, пока клиент явно не вызовет `ROLLBACK`. При отмене операции по `CancellationToken` сам токен пользователя переходит в состояние отмены, поэтому метод `RollbackAsync()` необходимо вызывать с передачей `CancellationToken.None` (или отдельного короткого CTS), иначе команда отката не дойдет до сервера из-за уже отмененного контекста.

### Задача 4. Потоковый экспорт BLOB через `SequentialAccess`
Реализована выгрузка больших бинарных объектов из базы данных на диск. Использован режим `CommandBehavior.SequentialAccess`, позволяющий читать данные из сетевого сокета последовательно порциями.

* **Ограничения SequentialAccess:** В режиме `SequentialAccess` данные выкачиваются из сетевого потока строго слева направо. Если попытаться прочитать первую колонку (индекс 0) после того, как была считана третья (индекс 2), Npgsql выбросит `InvalidOperationException`. Этот режим эффективен при работе с объектами размером более нескольких мегабайт (видео, изображения, архивы), так как предохраняет оперативную память приложения от переполнения (OutofMemory).

### Задача 5. Пакетные запросы `NpgsqlBatch` вместо MARS
Реализована одновременная выборка списка заказов и расчет их агрегированной суммы через отправку единого пакета команд.

* **Разница с MARS:** `NpgsqlBatch` не заменяет технологию MARS из MS SQL Server. MARS в SQL Server позволяет чередовать выполнение независимых команд и одновременно держать открытыми несколько активных `DataReader` на одном соединении. Батчинг в Npgsql работает иначе: он склеивает несколько SQL-выражений «паровозиком» и шлет их за один сетевой round-trip. На стороне сервера они все равно выполняются строго последовательно. Батчинг экономит время на сетевом пинге (задержках) до базы данных.

### Задача 6. Диагностика и лечение утечки пула соединений
Настроен пул соединений (`Maximum Pool Size=5; Timeout=5`). Продемонстрирована симуляция утечки ресурсов (connection leak), перехват ошибки исчерпания пула и принудительное восстановление приложения через `NpgsqlConnection.ClearAllPools()`.

* **Сравнение лимитов пула:** Лимит пула на клиенте задает максимальное количество одновременных TCP-соединений, которое может открыть конкретный запущенный экземпляр приложения. Параметр сервера `max_connections` — это глобальное ограничение СУБД PostgreSQL на количество подключений от всех клиентов суммарно (включая бэкапы, pgAdmin и другие микросервисы).

### Задача 7. Отказоустойчивый Health Check с прерыванием зависших сессий
Реализован компонент мониторинга доступности базы данных, автоматически отсекающий зависшие запросы с помощью серверной конфигурации `SET statement_timeout = 2000`.

* **Преимущество серверного таймаута:** Серверный `statement_timeout` просто прерывает «зависший» SQL-запрос (выдавая ошибку `57014`), но сохраняет сетевое соединение живым в пуле, защищая приложение от лишней нагрузки. Клиентский `CommandTimeout` в аналогичной ситуации привел бы к уничтожению физического TCP-соединения.

### Задача 8. Частичная обработка пакетов через `EnableErrorBarriers`
Продемонстрировано поведение батча при включенном флаге барьеров ошибок. Доказано, что без транзакции ошибочные команды отлавливаются изолированно через `NextResultAsync()`, не прерывая соседние успешные инструкции.

* **Ограничение транзакций:** Внутри явной транзакции свойство блокируется ядром СУБД, так как любое нарушение констреинта внутри блока `BEGIN ... COMMIT` мгновенно переводит всю транзакцию в состояние `aborted` и требует полного `ROLLBACK`.

### Задача 9. Управление параллелизмом через `SemaphoreSlim`
Реализован алгоритм троттлинга запросов. Использование асинхронного семафора на стороне C# позволяет выполнять пачки по 4 параллельных запроса из 30.

* **Назначение семафора:** Семафор удерживает потоки на уровне самого C#-приложения, не перегружая внутреннюю очередь пула драйвера, исключая падение пула по таймауту, даже если физический лимит пула соединений равен 5.

### Задача 10. Оптимистичная блокировка с использованием системного поля `xmin`
Реализован полноценный CRUD репозиторий, защищающий данные от коллизий при одновременном редактировании (Lost Update) без блокировки таблиц. 

* **Механизм xmin:** Метод `UpdateAsync` проверяет скрытое системное поле PostgreSQL `xmin`, хранящее ID транзакции последней модификации строки. Если строка была изменена параллельным процессом, генерируется `DBConcurrencyException`, предотвращая затирание данных.

## 🚀 Инструкция по локальному запуску

1. **Развертывание БД:** Установите PostgreSQL. Запустите графическую утилиту **pgAdmin**, создайте базу данных `npgsql_tasks`.
2. **Инициализация таблиц:** Скопируйте и запустите базовый SQL-скрипт инициализации (таблицы `employees`, `orders`, `accounts`, `batch_items`) в Query Tool.
3. **Настройка проекта:** Откройте созданное консольное приложение на **.NET 10** in Visual Studio.
4. **Установка драйвера:** Перейдите в Управление пакетами NuGet для проекта и установите пакет `Npgsql`.
5. **Строка подключения:** В файле `Program.cs` убедитесь, что в переменной `connectionString` указан ваш локальный пароль (например, `Password=1234;`).
6. **Тестирование:** Нажмите **F5** для запуска приложения.
